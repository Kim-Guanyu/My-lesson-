## 6.1 安装并整合Git服务端

**本课时对应知识点**：Git 概念、Git 安装、Git 存储分区、Git 整合到 IDEA。

**Git 是什么**。Git 是**分布式版本控制系统**（DVCS），由 Linus Torvalds 为管理 Linux 内核开发而创造。它记录文件每一次修改，可以随时回退到任意历史版本，并支持多人并行开发后合并。

**为什么需要版本控制**：不用手工维护 `项目_最终版.zip`、`项目_最终版2.zip`、`项目_真的最终版.zip`；能查到「这行代码是谁、什么时候、为什么改的」；改崩了能一键回退；多人改同一个项目不会互相覆盖。

**集中式 vs 分布式**（面试常问）：

| | 集中式（SVN） | 分布式（Git） |
|---|---|---|
| 版本库位置 | 只在中央服务器 | **每个人本地都有完整版本库** |
| 断网能否提交 | ❌ 不能 | ✅ 能，本地提交后再推送 |
| 服务器挂了 | 全员无法工作 | 本地照常工作，任一副本都能恢复 |
| 分支操作 | 慢（复制目录） | 极快（只是一个指针） |

**Git 的四个存储分区（核心概念，必须记牢）**：

```
① 工作区 Working Directory
      ↓  git add
② 暂存区 Stage / Index
      ↓  git commit
③ 本地仓库 Local Repository
      ↓  git push          ↑ git pull / git fetch
④ 远程仓库 Remote Repository
```

- **工作区** —— 你在电脑上实际看到和编辑的项目目录
- **暂存区** —— 一个「待提交清单」。`git add` 把改动放进来，作用是**让你能选择性提交**（改了 10 个文件，只想提交其中 3 个）
- **本地仓库** —— 项目目录下的隐藏目录 `.git`，保存全部提交历史。`git commit` 后改动进入这里，**此时已受版本控制保护，即使断网也不会丢**
- **远程仓库** —— GitHub / Gitee / GitLab 上的仓库，团队共享

**安装 Git**：官网 <https://git-scm.com/downloads> 下载（国内慢的话用淘宝镜像 <https://npmmirror.com/mirrors/git-for-windows/>）。安装时一路默认即可，注意勾选 `Git Bash Here`（右键菜单快捷入口）。

验证：任意目录右键 → `Git Bash Here`，执行 `git --version`。

**首次使用必须配置身份**（每次提交都会记录这个身份）：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
git config --global --list          # 查看全部配置
```

**整合到 IDEA**：`File → Settings → Version Control → Git`，`Path to Git executable` 指向 `D:\develop\Git\bin\git.exe`（或安装目录下的 `cmd\git.exe`），点右侧 **Test** 按钮，显示出 Git 版本号即成功。IDEA 一般能自动检测到。

**核心命令速查**：

```bash
git init                    # 初始化本地仓库（生成 .git 目录）
git status                  # 查看状态（最常用，随时敲）
git add 文件名               # 添加到暂存区
git add .                   # 添加全部改动
git commit -m "提交说明"     # 提交到本地仓库
git log                     # 查看提交历史
git log --oneline --graph   # 单行图形化历史
git diff                    # 查看未暂存的改动
git reset --hard 版本号      # 回退到指定版本（危险：丢弃改动）
git branch                  # 查看分支
git checkout -b 分支名       # 创建并切换分支
git merge 分支名             # 合并分支
```

**`.gitignore` 文件（很重要）**。声明哪些文件不纳入版本控制。Java 项目典型内容：

```gitignore
target/          # Maven 构建产物
*.class          # 字节码
.idea/           # IDEA 配置
*.iml
.env             # 含密钥的环境变量文件
logs/            # 日志
*.log
```

**原则：编译产物、IDE 配置、密钥、日志一律不提交**。特别是**密码和 API Key 绝对不能进 Git** —— 一旦推送到远程，即使后来删除，历史记录里依然能翻出来。

## 6.2 注册并整合Git远程库

**本课时对应知识点**：注册 GitEE 账号并整合 GitEE 到 IDEA。

**为什么用 Gitee**。Gitee（码云）是国内的代码托管平台，与 GitHub 功能类似。国内访问速度稳定，不需要额外网络配置，适合学习和国内团队协作。GitHub 是全球最大的开源社区，资源更丰富，但国内访问偶有波动。

**注册与准备**：

1. 访问 <https://gitee.com> 注册账号
2. **完成邮箱验证**（未验证无法推送代码）
3. 设置个人主页地址（将来仓库地址的一部分）

**方式一：IDEA 中登录 Gitee 账号**

先装 Gitee 插件（见 3.4 课时），然后 `File → Settings → Version Control → Gitee → Add Account`，输入账号密码或用 Token 登录。登录后就能在 IDEA 里直接分享项目、克隆仓库。

**方式二：配置 SSH 密钥（推荐，免去每次输密码）**

```bash
# 1. 生成密钥对（邮箱换成你 Gitee 注册用的）
ssh-keygen -t rsa -C "你的邮箱"
# 一路回车，默认生成到 ~/.ssh/

# 2. 查看公钥内容并复制
cat ~/.ssh/id_rsa.pub

# 3. 粘贴到 Gitee：设置 → SSH 公钥 → 添加

# 4. 测试连接
ssh -T git@gitee.com
```

看到 `Hi 用户名! You've successfully authenticated` 即成功。之后用 SSH 地址（`git@gitee.com:用户名/仓库名.git`）操作就不再需要输入账号密码。

**HTTPS 与 SSH 地址的区别**：

| | HTTPS | SSH |
|---|---|---|
| 地址格式 | `https://gitee.com/用户名/仓库.git` | `git@gitee.com:用户名/仓库.git` |
| 认证方式 | 每次输账号密码（或缓存凭据） | 密钥自动认证 |
| 适用 | 临时克隆公开仓库 | 日常开发（推荐） |

**关于密码认证**：Gitee 和 GitHub 都已逐步限制用账户密码直接推送，推荐使用 **SSH 密钥**或**私人访问令牌（Personal Access Token）**。GitHub 已完全停用密码认证。

## 6.3 分享项目到Git远程库

**本课时对应知识点**：创建项目，并分享项目到 GitEE。

**方式一：IDEA 一键分享（最简单）**

1. 打开要分享的项目
2. 菜单 `Git → GitHub/Gitee → Share Project on Gitee`
3. 填写仓库名（Repository name）、描述、是否私有（Private）
4. 点 Share → IDEA 自动完成：初始化本地仓库 → 添加文件 → 首次提交 → 在 Gitee 创建远程仓库 → 推送

**注意**：弹出的文件列表里要**取消勾选** `.idea/`、`target/`、`*.iml`，或者提前写好 `.gitignore`。

**方式二：命令行（理解原理，推荐至少手动做一次）**

先在 Gitee 网页上新建仓库（**不要**勾选「使用 Readme 文件初始化」，否则首次推送会冲突），然后：

```bash
cd 你的项目目录

git init                                      # ① 初始化本地仓库
echo "target/" > .gitignore                   # ② 写忽略规则
git add .                                     # ③ 添加到暂存区
git commit -m "init: 初始化项目"               # ④ 提交到本地仓库
git remote add origin git@gitee.com:用户名/仓库名.git   # ⑤ 关联远程仓库
git branch -M main                            # ⑥ 重命名主分支为 main
git push -u origin main                       # ⑦ 推送（-u 记住关联，以后直接 git push）
```

**`origin` 是什么**：远程仓库的**默认别名**，不是关键字。可以改成任意名字，只是约定俗成用 `origin`。一个项目可以关联多个远程仓库（如同时推 Gitee 和 GitHub）。

**`git push -u` 的 `-u` 是什么**：`--set-upstream` 的缩写，建立本地分支与远程分支的追踪关系。设置一次之后，以后直接 `git push` / `git pull` 即可，不用再写 `origin main`。

**首次推送常见错误**：

| 报错 | 原因与解决 |
|---|---|
| `failed to push some refs` / `fetch first` | 远程仓库有本地没有的提交（通常是建仓库时勾了 Readme）。先 `git pull --rebase origin main` 再推 |
| `Permission denied (publickey)` | SSH 公钥没配好，回到 6.2 重新配置 |
| `remote: [session-####] Access denied` | 账号无权限，或仓库地址写错了用户名 |
| `error: src refspec main does not match any` | 本地还没有任何提交，或分支名不是 main（用 `git branch` 确认） |

**提交信息的书写规范**（业界通行的 Conventional Commits）：

```
feat: 新增课程搜索功能
fix: 修复订单超时未取消的问题
docs: 更新 README 部署说明
style: 格式化代码，不影响逻辑
refactor: 重构订单服务，抽取公共方法
test: 补充用户服务的单元测试
chore: 升级 Maven 依赖版本
```

好的提交信息说明**为什么改**，而不只是**改了什么**（改了什么看 diff 就知道了）。避免 `update`、`修改`、`123` 这类无信息量的说明。

## 6.4 邀请队友到Git项目组

**本课时对应知识点**：邀请其他成员到 Git 项目组。

**操作路径**：Gitee 仓库页面 → `管理` → `仓库成员管理` → `添加仓库成员` → 输入对方的 Gitee 用户名或邮箱 → 选择权限 → 邀请。对方在消息中心接受邀请后生效。

**三种权限级别**：

| 角色 | 权限 |
|---|---|
| **观察者 Reporter** | 只能查看和克隆代码，不能推送 |
| **开发者 Developer** | 可以推送代码、创建分支、提 PR |
| **管理员 Master/Owner** | 可管理成员、设置仓库、删除仓库 |

**团队协作的两种模式**：

**① 团队成员模式（小团队常用）**。所有人都是同一个仓库的开发者，各自建分支开发，完成后合并到主分支。流程简单直接。

**② Fork + Pull Request 模式（开源项目标准）**：

```
原仓库 upstream
   ↓ Fork（复制一份到自己账号下）
我的仓库 origin
   ↓ Clone
本地开发 → 提交 → 推送到我的仓库
   ↓ 提交 Pull Request（Gitee 叫 Pull Request，GitHub 叫 Pull Request）
原仓库维护者审核 → 合并
```

优点是**外部贡献者不需要原仓库的写权限**，且所有改动都经过审核。参与开源项目走的都是这个流程。

**分支管理规范（Git Flow 简化版）**：

| 分支 | 用途 |
|---|---|
| `main` / `master` | 主分支，永远保持可发布状态，**禁止直接提交** |
| `develop` | 开发主分支，日常合并目标 |
| `feature/xxx` | 功能分支，从 develop 拉出，完成后合回 develop |
| `release/xxx` | 预发布分支，只修 bug 不加功能 |
| `hotfix/xxx` | 紧急修复分支，从 main 拉出，修完同时合回 main 和 develop |

**保护主分支**：Gitee 仓库 → 管理 → 分支设置 → 保护分支。可设置为「不允许直接推送，必须通过 Pull Request 合并」，并要求至少 N 人审核通过。这是团队协作的重要保障。

**冲突（Conflict）的产生与解决**。当两个人修改了同一文件的同一区域，合并时 Git 无法自动决定保留谁的，就产生冲突：

```java
<<<<<<< HEAD
System.out.println("我的版本");
=======
System.out.println("队友的版本");
>>>>>>> feature/other
```

解决步骤：① 手动编辑文件，删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记，保留最终想要的内容；② `git add 冲突文件`；③ `git commit`。

IDEA 提供图形化合并工具（`Git → Resolve Conflicts`），三栏对比左中右（我的 / 结果 / 对方），比手改标记直观得多，**强烈建议用它**。

**减少冲突的实践**：勤提交勤推送（改动小，冲突范围就小）；开始工作前先 `git pull`；不同人尽量不改同一文件；提前约定好代码格式（避免全文件因格式化产生"假冲突"）。

## 6.5 克隆项目到Git本地库

**本课时对应知识点**：使用 IDEA 克隆项目到本地、使用 Git 命令克隆项目到本地。

**方式一：命令行**

```bash
git clone git@gitee.com:用户名/仓库名.git              # SSH 方式（推荐）
git clone https://gitee.com/用户名/仓库名.git          # HTTPS 方式
git clone 地址 自定义目录名                             # 指定本地目录名
git clone -b develop 地址                              # 只克隆指定分支
git clone --depth 1 地址                               # 浅克隆，只取最近一次提交（仓库大时快很多）
```

`clone` 一步完成了：下载全部文件 + 下载完整提交历史 + 自动配置 `origin` 远程地址 + 检出默认分支。

**方式二：IDEA 克隆**

- 欢迎页 → `Get from VCS` → 粘贴仓库地址 → 选本地路径 → Clone
- 或已打开项目时：`File → New → Project from Version Control`

克隆后 IDEA 会自动识别项目类型。如果是 Maven 项目但没有识别，右键 `pom.xml` → `Add as Maven Project`。

**克隆后必做的三件事**：

1. **检查 JDK 配置** —— `File → Project Structure → Project SDK`，选择正确的 JDK 版本
2. **刷新 Maven 依赖** —— Maven 面板点 `Reload All Maven Projects`，等待依赖下载完成
3. **检查配置文件** —— `application.yml` 里的数据库地址、Redis 地址、密钥通常需要改成你自己的环境。密钥类配置往往被 `.gitignore` 排除了，需要向队友索要或按 `.example` 模板自建

**`clone` 与 `pull` 的区别**：`clone` 是**首次**获取整个仓库（本地还没有）；`pull` 是**后续**拉取别人的更新（本地已有仓库）。

```bash
git pull                    # 拉取并自动合并 = git fetch + git merge
git pull --rebase           # 拉取并变基（历史更线性、更整洁，推荐）
git fetch                   # 只下载不合并，可以先看看别人改了什么
```

## 6.6 推送代码到Git远程库

**本课时对应知识点**：使用 IDEA 推送修改后的内容、使用 Git 命令推送修改后的内容。

**命令行完整流程（日常开发标准动作）**：

```bash
git status                        # ① 看改了哪些文件
git add .                         # ② 加入暂存区
git commit -m "feat: 新增课程搜索"  # ③ 提交到本地仓库
git pull --rebase                 # ④ 先拉取别人的更新（重要！）
git push                          # ⑤ 推送到远程仓库
```

**第 ④ 步为什么必须做**：如果远程有你本地没有的提交，直接 push 会被拒绝（`failed to push some refs`）。先 pull 把别人的改动合进来，解决可能的冲突后再推。**养成"先拉后推"的习惯**能避免绝大多数推送失败。

**IDEA 中的操作**：

| 操作 | 快捷键 | 菜单 |
|---|---|---|
| 提交 | `Ctrl + K` | `Git → Commit` |
| 推送 | `Ctrl + Shift + K` | `Git → Push` |
| 拉取 | —— | `Git → Pull` |
| 提交并推送 | Commit 对话框里点 `Commit and Push` | —— |
| 查看历史 | —— | 底部 `Git` 窗口 → `Log` 标签 |

Commit 对话框里可以逐文件勾选、查看 diff、写提交信息。**推荐使用 `Commit and Push` 一步到位**。

**撤销操作速查（按场景选择）**：

```bash
# 改乱了，还没 add —— 丢弃工作区改动
git checkout -- 文件名
git restore 文件名                    # Git 2.23+ 的新写法

# 已经 add，还没 commit —— 取消暂存
git reset HEAD 文件名
git restore --staged 文件名           # 新写法

# 已经 commit，还没 push —— 撤销提交
git reset --soft HEAD~1               # 保留改动，回到暂存区
git reset --mixed HEAD~1              # 保留改动，回到工作区（默认）
git reset --hard HEAD~1               # 彻底丢弃改动（危险！）

# 已经 push —— 用反向提交（不要用 reset 改写已推送的历史）
git revert 提交ID                     # 生成一个新提交来抵消旧提交
```

**重要原则：已推送到共享分支的提交，不要用 `reset` + 强推（`push -f`）改写历史**。这会让所有队友的本地仓库与远程产生分歧，是团队协作中的严重事故。用 `git revert` 生成反向提交才是正确做法。

**紧急情况：`git reflog` 是后悔药**。它记录了 HEAD 的每一次移动，即使执行了 `reset --hard`，也能通过它找回丢失的提交：

```bash
git reflog                     # 找到误操作前的那个提交 ID
git reset --hard 那个提交ID     # 恢复
```

**本单元完整协作流程回顾**：

```
安装 Git → 配置身份 → 整合 IDEA
    ↓
注册 Gitee → 配置 SSH 公钥
    ↓
创建项目 → git init → 写 .gitignore → 分享到 Gitee
    ↓
邀请队友 → 分配权限 → 保护主分支
    ↓
队友 clone 到本地 → 建 feature 分支开发
    ↓
每日循环：add → commit → pull --rebase → push
    ↓
功能完成 → 提 Pull Request → 审核 → 合并到主分支
```
