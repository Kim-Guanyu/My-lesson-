## 4.1 Maven项目管理工具

**本课时对应知识点**：Maven 概念、快速构建项目功能、统一依赖管理功能。

**Maven 是什么**。Apache Maven 是 Java 项目的**构建工具 + 依赖管理工具**。它用一个 `pom.xml` 文件描述项目，然后按标准流程完成编译、测试、打包、安装、部署。

**没有 Maven 之前的痛点**（理解 Maven 价值的关键）：

1. **手动管依赖**。要用某个第三方库，得自己去官网下 jar 包，放进项目 `lib` 目录，再手动加到 classpath。
2. **依赖的依赖（传递依赖）要自己找**。下载了 A.jar，运行时报 `NoClassDefFoundError`，原因是 A 依赖 B，B 又依赖 C —— 得一层层手动补齐，非常痛苦。
3. **版本冲突无法管理**。两个库各自依赖同一个包的不同版本，谁生效完全靠运气。
4. **团队环境不一致**。「在我电脑上是好的」的经典来源。
5. **构建步骤靠人肉**。编译、跑测试、打包、部署每次手工执行，容易漏步骤。

**Maven 的两大核心功能**：

**① 统一依赖管理**。只需在 `pom.xml` 声明「我要什么」，Maven 自动从仓库下载 jar，**并自动下载它的所有传递依赖**：

```xml
<dependencies>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.42</version>
    </dependency>
</dependencies>
```

`groupId` + `artifactId` + `version` 三者合称 **GAV 坐标**，是 jar 包在仓库中的唯一地址。就像用「省 + 市 + 街道」定位一栋楼。

**② 快速构建项目**。Maven 定义了标准的**生命周期**，一条命令走完全流程：

```bash
mvn clean package    # 清理 → 编译 → 测试 → 打包
```

**Maven 的标准目录结构（约定优于配置）**：

```
project/
├── pom.xml                       项目描述文件（核心）
└── src/
    ├── main/
    │   ├── java/                 主代码
    │   └── resources/            主资源（配置文件 yaml/properties/xml）
    └── test/
        ├── java/                 测试代码
        └── resources/            测试资源
```

Maven 不需要你告诉它源码在哪 —— 它**约定**就在 `src/main/java`。这种「约定优于配置」的思想后面在 Spring Boot 里会再次见到。

**同类工具对比**：Ant（最早，全靠手写脚本，已淘汰）、**Maven**（约定优于配置，XML 描述，Java 生态主流）、**Gradle**（Groovy/Kotlin DSL 脚本，更灵活、构建更快，Android 官方选择）。企业 Java 后端目前仍以 Maven 为主。

**版本现状（2026 年 9 月）**：Maven **3.9.16** 是当前最新稳定版（2026 年 5 月发布）。Maven 4.0 仍在 rc 阶段，有较多变更，学习和生产都建议先用 3.9.x 系列。Maven 3.9+ 运行需要 JDK 8 及以上。

## 4.2 Maven管理工具安装

**本课时对应知识点**：检查 Maven 环境、下载 Maven 工具、配置 Maven 环境。

**① 检查是否已有 Maven**：

```bash
mvn -v
```

有输出就已安装（IDEA 自带一个捆绑版 Maven，但**建议单独装一个**，便于与命令行、Jenkins 等共用同一份配置和仓库）。

**② 下载**。官网 <https://maven.apache.org/download.cgi> 下载 **Binary zip archive**（如 `apache-maven-3.9.16-bin.zip`）。注意别下成 Source 源码包。解压到无中文无空格的路径，例如 `D:\develop\apache-maven-3.9.16`。

**目录结构**：

```
apache-maven-3.9.16/
├── bin/          可执行命令（mvn、mvn.cmd）
├── boot/         类加载器
├── conf/         配置目录 → settings.xml 就在这里
└── lib/          Maven 自身依赖的 jar
```

**③ 配置环境变量**（原理与第 2 单元配 JDK 完全一致）：

- 新建系统变量 `MAVEN_HOME` = `D:\develop\apache-maven-3.9.16`（**根目录**）
- 在 `Path` 中追加 `%MAVEN_HOME%\bin`

**④ 验证**（务必新开命令行窗口）：

```bash
mvn -v
```

正常输出示例：

```
Apache Maven 3.9.16
Maven home: D:\develop\apache-maven-3.9.16
Java version: 17.0.10, vendor: Oracle Corporation
Default locale: zh_CN, platform encoding: UTF-8
OS name: "windows 11"
```

**注意输出里的 `Java version`** —— Maven 依赖 `JAVA_HOME` 定位 JDK。如果这里报 `JAVA_HOME environment variable is not set`，说明第 2.3 课时的 `JAVA_HOME` 没配好，回去补上。

## 4.3 Maven本地仓库搭建

**本课时对应知识点**：Maven 仓库分类、Maven 获取依赖的线路、配置 Maven 本地仓库。

**仓库分三类**：

| 类型 | 位置 | 说明 |
|---|---|---|
| **本地仓库** | 自己电脑上，默认 `~/.m2/repository` | 所有下载过的 jar 都缓存在这里 |
| **远程仓库（私服）** | 公司内网，如 Nexus / Artifactory | 企业内部共享，也代理中央仓库 |
| **中央仓库** | <https://repo.maven.apache.org/maven2> | Apache 官方，全球最大的 Java 仓库 |

**依赖查找线路（务必记住这个顺序）**：

```
① 先找本地仓库 ~/.m2/repository
      ↓ 没有
② 再找私服 / 镜像（如果配了）
      ↓ 没有
③ 最后找中央仓库
      ↓ 下载成功
下载的 jar 存入本地仓库（下次直接命中①，不再联网）
```

这个机制解释了两个常见现象：**第一次构建特别慢**（大量下载），**之后就飞快**（全部命中本地缓存）；以及**断网也能构建**（依赖已在本地仓库）。

**配置本地仓库位置**。编辑 `conf/settings.xml`，找到 `<localRepository>` 节点（默认是注释掉的），改成：

```xml
<localRepository>D:\develop\maven-repository</localRepository>
```

**为什么要改**：默认位置在 C 盘用户目录下，而 Maven 仓库很容易膨胀到几个 GB，把它挪到 D 盘可以避免 C 盘爆满。

**配置国内镜像（必做，否则下载慢到无法忍受）**。中央仓库在国外，国内直连速度极慢甚至超时。在 `settings.xml` 的 `<mirrors>` 标签内加入阿里云镜像：

```xml
<mirrors>
    <mirror>
        <id>aliyunmaven</id>
        <mirrorOf>central</mirrorOf>
        <name>阿里云公共仓库</name>
        <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
</mirrors>
```

`<mirrorOf>central</mirrorOf>` 的含义是「凡是要访问 central 的请求，都改走这个地址」。用 `public` 聚合仓库比只镜像 `central` 覆盖面更广（它同时聚合了 central、jcenter 等）。

> 实践提醒：只配单一镜像存在单点故障风险，源一挂构建全失败。团队环境建议搭私服（Nexus）或配置备用源。可以用 `mvn help:effective-settings` 查看实际生效的配置。

**排查依赖下载失败**。如果某个依赖下载中断，本地仓库会残留 `.lastUpdated` 文件，Maven 会认为「已经试过了」而不再重试。解决办法是删除这些残留文件后重新构建：

```bash
# Windows PowerShell
Get-ChildItem -Path D:\develop\maven-repository -Filter *.lastUpdated -Recurse | Remove-Item
```

或者用 `mvn clean install -U` 强制更新快照与失败的依赖。

**查找依赖坐标的网站**：<https://mvnrepository.com>（最常用）、<https://central.sonatype.com>。搜索包名 → 选版本 → 复制 Maven 坐标粘贴进 `pom.xml`。

## 4.4 Maven管理工具整合

**本课时对应知识点**：将 Maven 工具整合到 IDEA 中。

IDEA 自带捆绑的 Maven，但版本可能与命令行不一致，且用的是默认仓库位置，会导致「命令行能构建，IDEA 里报错」这类困惑。整合的目的是**让 IDEA 用你自己装的那一套**。

`File → Settings → Build, Execution, Deployment → Build Tools → Maven`，改三处：

1. **Maven home path** → 选你解压的目录 `D:\develop\apache-maven-3.9.16`
2. **User settings file** → 勾选 `Override`，指向 `D:\develop\apache-maven-3.9.16\conf\settings.xml`
3. **Local repository** → 应自动读出 `settings.xml` 里配的路径（如 `D:\develop\maven-repository`）。若没变，手动勾 `Override` 填写

再看子菜单 `Maven → Importing`（新版在 Maven 主页面）：

- 勾选 `Import Maven projects automatically` —— 改完 `pom.xml` 自动同步依赖
- `JDK for importer` 选与项目一致的 JDK

**建议同时设为新项目默认值**：`File → New Projects Setup → Settings for New Projects` 里重复上面的配置，否则每建一个新项目都要重配一次。

**Maven 面板的常用操作**（右侧边栏 Maven 图标）：

- **Reload All Maven Projects**（刷新图标）—— 依赖没生效时第一时间点它
- **Lifecycle** —— 双击 `clean`、`compile`、`package`、`install` 执行生命周期阶段
- **Dependencies** —— 树形查看所有依赖及传递依赖
- **Plugins** —— 查看和执行插件目标

**依赖红线不消失的排查顺序**：① 点 Reload All Maven Projects；② 检查坐标拼写和版本是否真实存在（去 mvnrepository 核对）；③ 看 IDEA 底部 Build 窗口的具体报错；④ 删除本地仓库对应目录下的 `.lastUpdated` 文件重试；⑤ `File → Invalidate Caches → Invalidate and Restart`。

## 4.5 Maven父子项目创建

**本课时对应知识点**：Maven 父子项目（聚合工程）的创建方式。

**为什么需要父子项目**。一个真实项目往往拆成多个模块（如本平台的 `ml-common`、`ml-user`、`ml-course`、`ml-order`、`ml-gateway`）。如果每个模块各自声明依赖版本，很快就会出现「A 模块用 Spring 6.0、B 模块用 Spring 6.1」的混乱。父子结构解决两件事：**版本统一管理**和**一键构建全部模块**。

**父项目的 pom.xml**。关键是 `<packaging>pom</packaging>` —— 父项目不产出 jar，只做管理：

```xml
<project>
    <groupId>com.mdkj</groupId>
    <artifactId>my-lesson</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>pom</packaging>          <!-- 父项目必须是 pom -->

    <!-- 聚合：声明包含哪些子模块 -->
    <modules>
        <module>ml-common</module>
        <module>ml-user</module>
        <module>ml-course</module>
    </modules>

    <!-- 统一属性：版本号集中定义在一处 -->
    <properties>
        <maven.compiler.source>17</maven.compiler.source>
        <maven.compiler.target>17</maven.compiler.target>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <lombok.version>1.18.42</lombok.version>
    </properties>

    <!-- 依赖管理：只锁版本，不实际引入 -->
    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>${lombok.version}</version>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>
```

**子项目的 pom.xml**。用 `<parent>` 声明继承，引依赖时**不写版本号**（从父项目继承）：

```xml
<project>
    <parent>
        <groupId>com.mdkj</groupId>
        <artifactId>my-lesson</artifactId>
        <version>1.0-SNAPSHOT</version>
    </parent>

    <artifactId>ml-user</artifactId>          <!-- groupId 和 version 都继承父项目 -->

    <dependencies>
        <dependency>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
            <!-- 不写 version，由父项目 dependencyManagement 统一决定 -->
        </dependency>
    </dependencies>
</project>
```

**`<dependencies>` 与 `<dependencyManagement>` 的核心区别**（面试常问）：

| 标签 | 效果 |
|---|---|
| `<dependencies>` | **真实引入**，子项目自动继承这些依赖 |
| `<dependencyManagement>` | **只锁定版本**，不引入；子项目要用还得自己在 `<dependencies>` 里声明（但可省略版本号） |

所以父项目里应该：**所有模块都要用的**（如 lombok、hutool）放 `<dependencies>`；**部分模块才用的**（如 redis、mq）放 `<dependencyManagement>`。

**IDEA 中创建父子项目的操作**：先正常创建一个 Maven 项目作为父项目 → 删掉它的 `src` 目录（父项目不写代码）→ 在 `pom.xml` 中加 `<packaging>pom</packaging>` → 右键父项目 `New → Module` → 选 Maven → 创建。IDEA 会自动在父 pom 里补上 `<modules>`，并在子 pom 里补上 `<parent>`。

## 4.6 Maven一键构建测试

**本课时对应知识点**：`mvn clean` / `compile` / `test` / `package` / `install` 等命令。

**Maven 生命周期命令（按执行顺序）**：

| 命令 | 作用 | 产物 |
|---|---|---|
| `mvn clean` | 删除 `target` 目录 | 清空所有构建产物 |
| `mvn validate` | 校验项目配置是否正确 | —— |
| `mvn compile` | 编译主代码 | `target/classes/*.class` |
| `mvn test-compile` | 编译测试代码 | `target/test-classes/` |
| `mvn test` | 运行单元测试 | `target/surefire-reports/` 测试报告 |
| `mvn package` | 打包 | `target/xxx.jar` 或 `xxx.war` |
| `mvn verify` | 运行集成测试与检查 | —— |
| `mvn install` | 安装到**本地仓库** | jar 进入 `~/.m2/repository` |
| `mvn deploy` | 发布到**远程仓库/私服** | —— |

**关键规则：生命周期是累积的**。执行后面的阶段会**自动执行它前面的所有阶段**。所以 `mvn package` 实际上完成了 validate → compile → test → package 全过程。这也是为什么打包时会跑测试，测试失败会导致打包中断。

**最常用的组合命令**：

```bash
mvn clean package                          # 清理后重新打包（最常用）
mvn clean install                          # 打包并装进本地仓库（多模块项目必用）
mvn clean package -DskipTests              # 跳过测试打包（急着出包时用）
mvn clean install -U                       # 强制更新依赖（解决 .lastUpdated 问题）
mvn dependency:tree                        # 打印依赖树（排查版本冲突）
mvn help:effective-pom                     # 查看合并父项目后的完整 pom
mvn clean package -P prod                  # 指定 profile 环境打包
```

**`-DskipTests` 与 `-Dmaven.test.skip=true` 的区别**：前者**编译**测试代码但不**运行**；后者连测试代码都不编译。前者更常用。

**多模块项目为什么必须用 `install` 而不是 `package`**。假设 `ml-user` 依赖 `ml-common`：`package` 只把 `ml-common` 打成 jar 放在它自己的 `target` 目录里，`ml-user` 编译时到本地仓库找不到它 → 报 `Could not resolve dependencies`。`install` 会把 `ml-common` 装进本地仓库，`ml-user` 才能找到。**在父项目根目录执行 `mvn clean install`**，Maven 会按依赖顺序自动构建全部模块。

**关于 `property`（课时描述中提到的）**。`<properties>` 是自定义变量，用 `${变量名}` 引用，作用是把版本号等易变值集中到一处：

```xml
<properties>
    <spring.version>6.1.6</spring.version>
</properties>
...
<version>${spring.version}</version>
```

Maven 还内置了一批属性：`${project.version}`、`${project.artifactId}`、`${project.basedir}`、`${java.version}` 等。

**IDEA 中执行**：右侧 Maven 面板 → 展开模块 → Lifecycle → 双击对应命令。也可以点 Maven 面板的终端图标（`Run Maven Build`）手输命令。

**构建失败的通用排查思路**：① 从**第一个** `ERROR` 开始读，不要从最后一行读（后面的错误多是连带的）；② `BUILD FAILURE` 上方几行通常写明了具体原因；③ 依赖问题看 `Could not resolve` 后面的坐标是否拼错；④ 编译问题看具体文件和行号；⑤ 测试失败去 `target/surefire-reports/` 看详细报告。
