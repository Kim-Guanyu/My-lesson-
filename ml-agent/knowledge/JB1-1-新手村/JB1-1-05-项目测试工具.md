## 5.1 Junit测试的使用规范

**本课时对应知识点**：JUnit 测试类、测试方法、运行注解、前置注解、后置注解的规范。

**为什么需要单元测试**。初学阶段验证代码都靠 `main()` 方法加 `System.out.println()`，问题是：验证完要删掉、无法批量运行、无法自动判断对错（得靠人眼看输出）、改了代码不知道有没有破坏原有功能。**单元测试把「验证」变成可重复执行、可自动判定的代码**。

**JUnit 版本说明（2026 年现状）**。JUnit 5 引入了全新架构（Jupiter），包名是 `org.junit.jupiter.api`。目前 JUnit 已发展到 **6.x**（如 6.1.3），但**包名与注解 API 与 JUnit 5 完全一致**，迁移成本极低。老项目还有大量 JUnit 4（包名 `org.junit`，注解是 `@Before` / `@After`）。本课程按 JUnit 5 讲解。

**测试类规范**：

- 类名 = 被测类名 + `Test` 后缀，如 `UserServiceTest`
- 放在 `src/test/java` 下，包结构与主代码**保持一致**（这样测试类能访问被测类的包级私有成员）
- 测试类本身**不需要** `public`（JUnit 5 允许包级私有）

**测试方法规范**：

- 方法必须**无返回值（void）**、**无参数**（或只有能被 `ParameterResolver` 解析的参数如 `TestInfo`）
- **不能是 static**（`@BeforeAll` / `@AfterAll` 例外，它们必须 static）
- 不建议用 `private`（JUnit 5 直接禁止；JUnit 6 中强烈不推荐，未来版本将禁止）
- 命名建议用 `test业务点` 或直接描述行为，如 `testAddUser`、`whenPriceIsNegative_thenThrowException`

**五个核心注解**：

| 注解 | 时机 | 要求 |
|---|---|---|
| `@Test` | 标记这是一个测试方法 | 必须 void 无参 |
| `@BeforeEach` | **每个**测试方法**之前**执行（前置） | 非 static |
| `@AfterEach` | **每个**测试方法**之后**执行（后置） | 非 static |
| `@BeforeAll` | 整个测试类**只执行一次**，最先 | **必须 static** |
| `@AfterAll` | 整个测试类**只执行一次**，最后 | **必须 static** |

**完整示例**：

```java
package com.mdkj.service;

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {

    private Calculator calculator;

    @BeforeAll
    static void initAll() {
        System.out.println("① 整个测试类开始前，执行一次");
    }

    @BeforeEach
    void init() {
        calculator = new Calculator();   // 每个用例前重建对象，保证用例之间互不干扰
        System.out.println("② 每个测试方法前都执行");
    }

    @Test
    @DisplayName("加法：1 + 1 应该等于 2")
    void testAdd() {
        assertEquals(2, calculator.add(1, 1), "1 + 1 应该等于 2");
    }

    @Test
    void testDivideByZero() {
        // 断言会抛出指定异常
        assertThrows(ArithmeticException.class, () -> calculator.divide(1, 0));
    }

    @Test
    @Disabled("功能未完成，暂时跳过")
    void testNotReady() { }

    @AfterEach
    void tearDown() {
        System.out.println("③ 每个测试方法后都执行");
    }

    @AfterAll
    static void tearDownAll() {
        System.out.println("④ 整个测试类结束后，执行一次");
    }
}
```

**执行顺序**：`@BeforeAll` → (`@BeforeEach` → `@Test` → `@AfterEach`) × N 个测试方法 → `@AfterAll`。

**为什么 `@BeforeAll` 必须 static**：它在任何测试实例创建之前就要执行，此时还没有对象，只能通过类调用 —— 与 `main()` 方法必须是 static 的原因完全一样（见 2.5 课时）。误写成非 static 会直接报错：`@BeforeAll method must be static`。

**常用断言方法**（`org.junit.jupiter.api.Assertions`）：

```java
assertEquals(expected, actual);          // 相等（第一个参数是期望值）
assertNotEquals(unexpected, actual);     // 不相等
assertTrue(condition);                   // 为真
assertFalse(condition);                  // 为假
assertNull(obj);                         // 为 null
assertNotNull(obj);                      // 不为 null
assertSame(expected, actual);            // 同一个对象引用（==）
assertArrayEquals(expectedArr, actualArr);
assertThrows(异常类.class, () -> 代码);   // 断言抛出指定异常
assertTimeout(Duration.ofSeconds(1), () -> 代码);  // 断言在时限内完成
assertAll(() -> assertEquals(...), () -> assertTrue(...));  // 全部执行后统一报告
```

**其他实用注解**：`@DisplayName("中文用例名")` 自定义显示名；`@Disabled` 临时禁用；`@RepeatedTest(5)` 重复执行；`@ParameterizedTest` + `@ValueSource` 参数化测试；`@Tag("slow")` 打标签便于按组过滤；`@Timeout(3)` 超时限制。

**JUnit 4 与 JUnit 5 注解对照**（维护老项目时需要）：

| JUnit 4 | JUnit 5 |
|---|---|
| `@Before` | `@BeforeEach` |
| `@After` | `@AfterEach` |
| `@BeforeClass` | `@BeforeAll` |
| `@AfterClass` | `@AfterAll` |
| `@Ignore` | `@Disabled` |
| `@Test(expected=X.class)` | `assertThrows(X.class, ...)` |
| `@Test(timeout=1000)` | `@Timeout` |

**两个执行顺序上的坑**：JUnit 不保证同一类中**多个** `@BeforeEach` 方法之间的执行顺序；`@BeforeEach` 与 `@AfterEach` 之间**没有配对关系**，不要指望它们形成包裹式的对称行为。

## 5.2 Junit依赖的生效范围

**本课时对应知识点**：`property`、`compile`、`runtime`、`provided`、`test` 等依赖范围（scope）。

**什么是依赖范围**。`<scope>` 决定一个依赖在**哪些阶段的 classpath 中可见**，以及**是否随项目一起打包**。用对 scope 能显著减小包体积并避免依赖污染。

| scope | 编译主代码 | 编译测试 | 运行时 | 是否打进包 | 典型例子 |
|---|---|---|---|---|---|
| **compile**（默认） | ✅ | ✅ | ✅ | ✅ | 绝大多数依赖，如 hutool |
| **test** | ❌ | ✅ | ❌ | ❌ | **JUnit**、Mockito |
| **provided** | ✅ | ✅ | ❌ | ❌ | Servlet API、Lombok |
| **runtime** | ❌ | ✅ | ✅ | ✅ | MySQL 驱动、日志实现 |
| **system** | ✅ | ✅ | ❌ | ❌ | 本地 jar（已不推荐） |
| **import** | —— | —— | —— | —— | 仅用于 `dependencyManagement` 导入 BOM |

**逐个理解**：

**compile（默认）** —— 全阶段可见，随包发布。不写 `<scope>` 就是它。

**test** —— **只在测试阶段可见**。JUnit 就应该用它：主代码里写 `import org.junit...` 会直接编译报错（这是好事，防止测试代码混进生产代码），打成的 jar 里也不含 JUnit，包更小。

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>          <!-- 关键 -->
</dependency>
```

**provided** —— 「**编译时需要，运行时由容器提供**」。典型是 Servlet API：写代码时要用 `HttpServletRequest` 所以编译期需要，但运行时 Tomcat 自带这个 jar，如果再打进 war 包会**冲突报错**。Lombok 也常用 provided（它只在编译期生成代码，运行时不需要）。

**runtime** —— 「**编译时不需要，运行时才需要**」。典型是 JDBC 驱动：代码里只写 `Class.forName("com.mysql.cj.jdbc.Driver")` 或通过 SPI 加载，编译期并不直接 import 驱动类，但运行时必须存在。

**关于 `property`**。课时描述里提到的 `property` 不是 scope，而是 `<properties>` 标签 —— 用来定义变量、集中管理版本号（见 4.6 课时）。它与 scope 是两个概念，容易混淆：

```xml
<properties>
    <junit.version>5.10.2</junit.version>       <!-- 定义变量 -->
</properties>
...
<version>${junit.version}</version>            <!-- 引用变量 -->
```

**依赖范围的传递性**。A 依赖 B（compile），B 依赖 C：C 的 scope 决定它对 A 是否可见。简单记：**test 和 provided 不传递**。这就是为什么你的项目引入了某个框架，却用不到它内部测试用的 JUnit。

**查看实际生效的依赖及范围**：

```bash
mvn dependency:tree
```

## 5.3 Junit依赖的版本管理

**本课时对应知识点**：在父项目中锁定 JUnit 依赖的版本并管理该依赖。

**问题场景**。多模块项目里，`ml-user` 用 JUnit 5.10.2，`ml-course` 用 5.9.0，`ml-order` 忘了写版本 —— 三个模块行为不一致，排查问题时极易踩坑。

**解决方案：在父项目用 `<dependencyManagement>` 锁定版本**。

父项目 `pom.xml`：

```xml
<properties>
    <junit.version>5.10.2</junit.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>${junit.version}</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

**注意：`<dependencyManagement>` 只是「声明版本」，不会真的引入依赖**。子模块此时还用不了 JUnit —— 这正是下一课时要做的事。

**用 BOM 管理（更推荐的现代做法）**。JUnit 官方提供了 BOM（Bill of Materials 物料清单），一次导入即可锁定 JUnit 全家桶的版本：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>5.10.2</version>
            <type>pom</type>
            <scope>import</scope>       <!-- 这就是 import scope 的用途 -->
        </dependency>
    </dependencies>
</dependencyManagement>
```

之后子模块引 `junit-jupiter`、`junit-jupiter-params`、`junit-platform-launcher` 都不用写版本，且它们之间的版本一定兼容。Spring Boot 的 `spring-boot-dependencies` 就是同样的机制。

**为什么要统一版本**：① 避免不同模块行为不一致；② 避免依赖冲突（同一个 jar 出现多个版本时，Maven 按「最短路径优先、路径相同则先声明优先」的规则仲裁，结果往往出人意料）；③ 升级时只改一处。

**顺带配置 Surefire 插件**。Maven 靠 `maven-surefire-plugin` 执行测试。自 Surefire 3.6.0 起总是使用 JUnit Platform provider，通常只要保证插件版本够新：

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.6.0</version>
        </plugin>
    </plugins>
</build>
```

**老项目混用 JUnit 4 和 5 时**，还需要引入 Vintage 引擎，否则 JUnit 4 的用例不会被执行：

```xml
<dependency>
    <groupId>org.junit.vintage</groupId>
    <artifactId>junit-vintage-engine</artifactId>
    <scope>test</scope>
</dependency>
```

## 5.4 Junit依赖的真实引入

**本课时对应知识点**：在子项目中引入 JUnit 依赖。

父项目锁好版本后，**子模块必须自己在 `<dependencies>` 中声明才真正拥有这个依赖**，但可以省略 `<version>` 和 `<scope>`（都从父项目继承）：

```xml
<!-- 子模块 ml-user 的 pom.xml -->
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <!-- 无 version：由父项目 dependencyManagement 决定 -->
        <!-- 无 scope：继承父项目声明的 test -->
    </dependency>
</dependencies>
```

**`junit-jupiter` 是聚合工件**，包含三部分：

| 工件 | 作用 |
|---|---|
| `junit-jupiter-api` | 编写测试用的 API（`@Test`、`Assertions`） |
| `junit-jupiter-engine` | 运行时引擎，负责真正执行测试 |
| `junit-jupiter-params` | 参数化测试支持 |

直接引聚合包 `junit-jupiter` 最省事。只引 `junit-jupiter-api` 会出现「代码能写、能编译、但测试跑不起来」的现象 —— 因为缺少引擎。

**完整流程回顾**（把本单元四个课时串起来）：

```
① 父项目 <properties> 定义版本变量
② 父项目 <dependencyManagement> 锁定 JUnit 版本 + scope=test
③ 子项目 <dependencies> 声明 JUnit（不写版本）
④ 在 src/test/java 下写测试类，用 @Test / @BeforeEach 等注解
⑤ 执行 mvn test 或在 IDEA 中点行号旁的绿色三角运行
```

**验证依赖是否真的生效**：

```bash
mvn dependency:tree | grep junit
```

应看到 `org.junit.jupiter:junit-jupiter:jar:5.10.2:test`，末尾的 `test` 就是生效的 scope。

**IDEA 中运行测试的方式**：① 点方法左侧绿色三角 → 运行单个测试方法；② 点类名左侧绿色三角 → 运行整个测试类；③ 右键 `src/test/java` → `Run All Tests` → 运行全部；④ 快捷键 `Ctrl + Shift + F10`。

**结果解读**：绿色对勾 = 通过；红色叉 = 断言失败或抛出异常（点开看 `Expected` 与 `Actual` 的差异）；黄色 = 被 `@Disabled` 跳过。

**四个高频问题**：

| 现象 | 原因 |
|---|---|
| 测试方法左边没有绿色三角 | 依赖没引入或未 Reload Maven；也可能测试类放错了目录（必须在 `src/test/java`） |
| `NoClassDefFoundError: org/junit/platform/...` | 只引了 `junit-jupiter-api`，缺少 engine，改引聚合包 `junit-jupiter` |
| 主代码里 import JUnit 报错 | 正常现象 —— `scope=test` 的依赖对主代码不可见，测试代码应放在 `src/test/java` |
| `mvn test` 不执行任何用例 | Surefire 插件版本过旧，或测试类名不符合 `*Test` / `Test*` / `*Tests` 命名约定 |

**测试的实践建议**：一个测试方法只验证一个行为；测试之间**必须相互独立**（用 `@BeforeEach` 重建对象，不要依赖执行顺序）；测试数据不要依赖真实数据库（用内存库或 Mock）；断言要具体（`assertEquals(2, result)` 优于 `assertTrue(result > 0)`）。
